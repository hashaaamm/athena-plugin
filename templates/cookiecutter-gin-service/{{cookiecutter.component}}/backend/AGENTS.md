## Layout

```
cmd/
├── api/main.go          # the binary: serve | {% if cookiecutter.use_postgres == "yes" %}migrate up|down|status | {% endif %}healthcheck
└── openapi/             # build tool: swag's Swagger 2.0 -> the OpenAPI 3 document (never linked into api)
internal/
├── app/                 # THE composition root: wire.go builds the graph, server.go runs it
├── config/              # the ONLY place the environment is read
├── http/
│   ├── router.go        # every route, the middleware order{% if cookiecutter.use_postgres == "yes" %}, and the public/private split{% endif %}
│   ├── handler/         # bind -> one service call -> write; wire types (schema.go)
│   └── middleware/      # errors + recovery, {% if cookiecutter.use_postgres == "yes" %}RequireActor, CSRF, {% endif %}CORS, request log, body limit
├── service/             # one method per use case; returns apperr, never a status code
{%- if cookiecutter.use_postgres == "yes" %}
├── repository/          # every query; Store.WithTx owns commit/rollback; the ONLY importer of db and pgx
├── db/                  # sqlc output — generated, committed, drift-checked
├── security/            # passwords (Argon2id + semaphore), tokens (JWT), actor
├── testdb/              # the suite's Postgres: a schema per package, a rolled-back tx per test
{%- endif %}
{%- if cookiecutter.use_sentry == "yes" %}
├── observability/       # Sentry: init, per-request hub, scrubbing
{%- endif %}
└── apperr/              # error vocabulary and the one error envelope
{%- if cookiecutter.use_postgres == "yes" %}
migrations/              # goose SQL, embedded in the binary; also sqlc's schema
queries/                 # sqlc .sql files
{%- endif %}
docs/                    # openapi.json{% if cookiecutter.use_postgres == "yes" %} + openapi-cookie.json{% endif %} — generated, committed, embedded
```

The flow is one-directional: `handler -> service -> repository -> db`. Never skip a layer, never
call backwards. A handler makes exactly one service call and maps its result to a wire type; a row
from `internal/db` never leaves the repository. `just lint` enforces it — the depguard rules in
`.golangci.yml` fail the build when a handler imports the repository, a service imports `net/http`
or gin, anything but the repository imports `internal/db` or pgx, or anything but `internal/config`
reads the environment.

{% if cookiecutter.use_postgres == "yes" -%}
**Authentication is the worked example, and it runs through every layer.** `handler/auth*.go`
binds input and calls one method on `service.AuthService`; the service owns every rule about
passwords, enumeration and sessions; `repository.UserRepository` and `RefreshSessionRepository` own
every query, written in `queries/` and generated by sqlc; `migrations/` are the tables. Read it
before you write the second resource, because it is the shape the second one takes. It is a real
feature — `register`, `login`, `refresh`, `logout`, `me` and `change-password`, with the same routes,
status codes, JSON and error envelope as the FastAPI template, so its React client works unchanged.

**Sessions.** Login returns an access token (fifteen minutes) and a refresh token (thirty days,
single-use). Each refresh revokes the token it spent and issues the next one in the same family,
with the row locked `FOR UPDATE`; a spent token presented again revokes the whole family. Logout
revokes the family and never fails. Changing a password revokes every family and gives the caller a
new one. The refresh token is refused as a bearer token. Where it travels is `REFRESH_TRANSPORT`:
`body` (default — JSON both ways, `handler/auth_body.go`) or `cookie` (an httpOnly cookie with a CSRF
check on refresh and logout, `handler/auth_cookie.go`, for a browser client). The router mounts one
set; the service never knows which.

**Two rules this leans on.** A refused request rolls back its writes, except
`apperr.CompromisedSession`, whose family revocation is the point of the refusal — use that error, or
the revocation silently disappears with the 401. And revocation latency is fifteen minutes: revoking
a session stops new access tokens at once, and the access token already issued keeps working until
it expires. That is the documented trade for not reading the database on every request;
deactivating a user is the same sentence.

What it deliberately leaves out, so you do not assume it is there: no roles or permission checks, no
ownership checks, no password reset, no email verification, and no scheduled job deleting expired
`refresh_sessions` rows — add one before the table matters, never on the refresh path. Ask Athena for
the JWT authentication guide before adding any of them.
{%- else -%}
The only endpoints shipped are the health probes, so read the layering as a rule rather than as
something the code demonstrates end to end. With no database there is no repository: `HealthService`
has no dependencies, and handler -> service is all the flow there is to see. There is no
authentication either — a user table is what a password is checked against, and this service has no
tables at all. The first resource you add is what makes the rest of it real.
{%- endif %}

## Rules specific to this service

{% if cookiecutter.use_postgres == "yes" -%}
1. Nothing commits except `repository.Store.WithTx`. Every write a use case makes runs inside one
   `WithTx` call in the service, and the service returns only after the commit — so the handler has
   not written a byte when a commit fails, and the client gets a 500 instead of a 2xx for a write
   that never happened. Inside `WithTx`, use the `tx` store it hands you: a query on the outer store
   runs on another connection, outside the transaction and its locks. Never hold a transaction open
   across slow work — Argon2 runs before `WithTx`, not inside it.
2. No `os.Getenv` outside `internal/config`. Add a field to `config.Config`, with its default, its
   validation and a test.
3. Every error a handler can return goes through `handler.Fail`; only the error middleware writes
   error responses. Deliberate failures are `apperr` values; anything else is a 500 with a trace id.
   Wrap errors with what was being done (`fmt.Errorf("create invoice: %w", err)`) — Go errors carry
   no stack, and the message chain is how a 500 is located.
4. Every route carries swag annotations — `@Summary`, `@ID`, `@Tags`, `@Param`, every `@Success`
   and `@Failure` it can answer, `@Security BearerAuth` when it is private — and wire types carry
   `// @name`. Then `just gen`. CI fails on a stale `docs/openapi.json`.
5. A password digest never leaves the data layer. It is not on a service or wire type, not in a log
   line, not in an error message; `repository.PasswordDigest` prints as `[redacted]` so a stray `%+v`
   cannot leak one.
6. A new route goes on `private` in `internal/http/router.go` unless there is a stated reason it is
   open. Deny by default is enforced there, not route by route.
7. Every SQL change is a new goose migration (`just db-new`), never an edit to one that has run
   anywhere. Name every constraint and index explicitly, and keep it backward-compatible with the
   code already deployed: the migrate job runs before the new revision takes traffic.
8. `DATABASE_AUTH` says how a process reaches Postgres: `password` (the default — local, tests, CI,
   and the deployed migrate job), `rds-iam` or `cloud-sql-iam` (the deployed service, which holds
   no database password). The pool is built in one place, `internal/app/database.go`; an IAM mode
   sets the password per connection or dials through the Cloud SQL connector, and nothing else in
   the code knows which. The service's role has row privileges only, granted by `migrate up` after
   every run — a migration may create tables, and the grants follow it by default privileges, but
   a migration that needs the service to do something new (a `TRUNCATE`, a function) needs the
   grant in `internal/app/migrate.go`'s `appGrants` too.

## Where to start when adding a resource

{% if cookiecutter.use_postgres == "yes" -%}
Read the auth resource end to end first. Then write the same pieces for yours, in this order, and
skip none of them:

1. `just db-new create_<x>` — the table, in `migrations/`, with named constraints and a Down section.
2. `queries/<x>.sql` — every query, and `just gen` to generate `internal/db`.
3. `internal/repository/<x>.go` — a `<X>Repository` over `*db.Queries`, an accessor on `Store`, and
   the repository's own type mapped from the row. Every query, and nothing else.
4. `internal/service/<x>.go` — one exported method per use case, writes inside `WithTx`, returning
   service types and `apperr` values.
5. `internal/http/handler/<x>.go` and wire types in `schema.go` — bind, one service call, write;
   annotated for swag.
6. Wire it in `internal/app/wire.go`, and add its routes in `internal/http/router.go` — **on
   `private` unless you can say out loud why an anonymous caller may have this**.

Then `just gen`, and tests: the service's rules directly (`internal/service`, against `testdb`), the
routes through the router (`internal/app`), and `just check`.
{%- else -%}
There is no example resource to copy — with no database the template ships the health endpoints and
nothing else, so the first one is written rather than renamed. It is the same files every time, in
this order, and none of them may be skipped:

1. `internal/service/<x>.go` — one exported method per use case, returning service types and
   `apperr` values, never a status code.
2. `internal/http/handler/<x>.go` and wire types in `schema.go` — bind (`handler.BindJSON`), one
   service call, write; annotated for swag.
3. Wire it in `internal/app/wire.go` and add its routes in `internal/http/router.go`. Then `just gen`.

A repository joins that list the moment this service gets a database — which is a
`use_postgres=yes` regeneration, not a hand-rolled connection. Authentication arrives with it, which
is the other thing a database turns on here.
{%- endif %}
